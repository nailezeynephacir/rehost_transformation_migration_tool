## 1. Parser sorunları
### 1.1. `__attribute__` fonksiyon adı sanılıyor — düzeltilmeli

Örnek:

```c
int read_sensor(void) __attribute__((used)) {
    return 1;
}
```

Mevcut parser çıktısı:
```text
name = "__attribute__"
signature = "int read_sensor(void) __attribute__((used))"
```

Doğru fonksiyon adı `read_sensor` olmalı.

Sebep: `extract_function_name()` imzadaki son uygun üst seviye parantezi seçiyor. Buradaki son parantez fonksiyon parametrelerine değil, `__attribute__` ifadesine ait.

Etkisi:
* Conditional block yanlış fonksiyon adıyla kaydediliyor.
* Yeni projede `read_sensor` yerine `__attribute__` aranıyor.
* Transformation uygulanamıyor ve `function not found` ile atlanabiliyor.

---

### 1.2. Fonksiyon pointer döndüren fonksiyonun adı yanlış bulunuyor — kapsam kararı gerekli
Örnek:
```c
int (*factory(void))(int) {
    return 0;
}
```

Mevcut sonuç:
```text
name = "int"
```

Doğru sonuç:
```text
name = "factory"
```

Bu da function-scope transformation eşleştirmesini bozuyor.

Karar verilmesi gereken nokta:
* Hedef projelerde bu imza desteklenecekse parser düzeltilmeli.
* Desteklenmeyecekse açıkça belgelenmiş bir parser sınırlaması olmalı.

---

### 1.3. Çok satırlı `#define`, sonraki fonksiyonun imzasına karışıyor — düzeltilmeli
Örnek:

```c
#define CHECK(x) do { \
    x; \
} while (0)

int read_sensor(void) {
    return 1;
}
```

Parser fonksiyon adını doğru buluyor ancak imzayı şöyle kaydediyor:
```text
while (0)
int read_sensor(void)
```

Sebep: `find_signature_start_index()` yalnızca `#` ile başlayan fiziksel satırı preprocessor satırı kabul ediyor. `\` ile devam eden satırları direktifin parçası olarak görmüyor.

Etkisi:
* Yanlış `function_signature` JSON’a yazılıyor.
* Yeni projede aynı makronun biçimi değişirse fonksiyon imzası değişmiş sanılabiliyor.
* Güvenli bir transformation gereksiz yere `SKIPPED` olabiliyor.

---

### 1.4. Conditional alternatifler brace dengesini değiştiriyorsa fonksiyon bulunamıyor — mimari sınırlama
Örnek:
```c
void configure(void) {
#if REHOST_MODE
    if (windows_mode) {
#else
    if (embedded_mode) {
#endif
    }
}
```

Kod preprocessing sonrasında her iki modda da dengeli olabilir. Fakat parser iki branch’i aynı anda aktif C kodu gibi değerlendiriyor. Böylece iki `{` ve yalnızca bir `}` görüyor.

Sonuç:
* `configure` fonksiyonu bulunamıyor.
* `unbalanced braces` warning oluşuyor.
* Conditional block `function` yerine `global` sınıflandırılıyor.
* Pipeline parser warning gördüğü için dosyanın dönüşümlerini atlıyor.

Bu basit bir regex hatasından çok parser mimarisiyle ilgili. Fonksiyon sınırlarını belirlerken preprocessor branch’lerinin nasıl ele alınacağına karar verilmesi gerekiyor.

En azından aşağıdaki seçeneklerden biri seçilmeli:
* Target macro için branch-aware brace analizi yapmak.
* Her olası branch’i ayrı ayrı analiz etmek.
* Bu yapıyı desteklenmeyen ve güvenli biçimde `SKIPPED` edilen bir durum olarak belgelemek.

---

### 1.5. Boş `#else`, include bloğunu global sınıflandırıyor — düşük öncelik
Boş `#else` bulunan include conditional’ı `include` yerine `global` olabiliyor.
Bu durumun oluşma ihtimali düşük görüldüğü için şimdilik atlandı. İleride scope sınıflandırması daha katı olacaksa düzeltilebilir.

---

### 1.6. İkinci `#else` warning oluşturuyor fakat blok içeriğine de karışıyor — düşük öncelik
Geçersiz bir conditional içinde ikinci `#else` bulunduğunda parser warning üretiyor fakat ilgili direktif/metin oluşturulan bloğun içeriğine de girebiliyor.
Pipeline parser warning varsa extraction/application yapmadığı için şu anda güvenli davranıyor; yanlış transformation uygulanmıyor.
Ancak parser çıktısının kendi başına tutarlı olması isteniyorsa:
* Geçersiz blok hiç oluşturulmamalı veya
* Blok `invalid` olarak işaretlenmeli.

---

### 1.7. C++ desteğinin kapsamına karar verilmeli
Parser şu yapılardaki fonksiyonları bulamıyor:
```cpp
namespace example {
    int read() {
        return 1;
    }
}
```

```cpp
class Sensor {
    int read() {
        return 1;
    }
};
```

```cpp
extern "C" {
    int read_sensor() {
        return 1;
    }
}
```

Aşağıdaki modern C++ imzaları da yanlış fonksiyon adı veya yanlış signature üretebilir:

```cpp
int read() noexcept(condition) {
}
```

```cpp
auto read() -> int {
}
```

```cpp
int read() requires SomeConcept<T> {
}
```

Burada kod değişikliğinden önce kapsam kararı gerekiyor:

* Araç genel C++ desteği vaat edecek mi?
* Yoksa `.cpp` desteği “yalnızca sıradan top-level fonksiyonlar” ile mi sınırlandırılacak?
Genel C++ desteği amaçlanıyorsa mevcut el yapımı parser’ı genişletmek giderek riskli hale gelecektir. Bu durumda gerçek bir C/C++ parser kullanılması değerlendirilmelidir.

## 2. Extraction sorunları
### 2.1. Fonksiyon içindeki aynı kodun bütün eşleşmeleri dönüştürülüyor — güvenlik kararı gerekli

Original:

```c
void f(void) {
    work();
    work();
}
```

Eski rehost’ta yalnızca ilk `work()` conditional içine alınmış olsa bile extraction tek transformation oluşturuyor:

```json
{
    "match": "work();"
}
```

Apply aşaması fonksiyondaki iki `work()` çağrısını da dönüştürüyor. Testte `applied_count = 2` çıktı.

Bu, aracın güvenli çalışma prensibine aykırı çünkü konum bilgisi olmadan hangi occurrence’ın dönüştürülmesi gerektiğini bilmiyoruz.

Önerilen güvenli davranış:

```python
if len(matches_to_apply) > 1:
    SKIPPED
```

Fonksiyon scope’unda multiple match’e izin verme kararı yeniden değerlendirilmelidir. Birden fazla occurrence desteklenmek isteniyorsa JSON’da güvenilir konum veya anchor bilgisi tutulması gerekir.

---

### 2.2. Aynı `match` değerine sahip transformation çakışmaları kontrol edilmiyor — düzeltilmeli
Aynı fonksiyondaki iki farklı conditional block şu branch’i kullanabilir:

```c
work();
```

Extraction bu durumda iki transformation üretebiliyor:
```text
conditional_1 → match: work();
conditional_2 → match: work();
```

Apply sırasına bağlı olarak:
* İlk transformation bütün `work()` eşleşmelerini değiştirebilir.
* İkinci transformation, ilkinin eklediği conditional’ın içindeki `work()` kodunu tekrar bulabilir.
* Farklı conditional block’lar yanlışlıkla iç içe geçirilebilir.

Extraction en azından şu kombinasyonda çakışma kontrolü yapmalı:

```text
file + scope + function + normalized match
```

Çakışma bulunduğunda transformation’lar otomatik uygulanabilir olarak üretilmemeli; `SKIPPED`, `NEEDS_REVIEW` veya benzeri bir durum seçilmeli.

---

### 2.3. `before` anchor insertion girintiyi bozuyor

Extraction şu transformation’ı üretebiliyor:

```json
{
    "operation": "insert",
    "position": "before",
    "anchor": "after();"
}
```

Apply sonucu:

```c
void f(void) {
    before();
    
#ifdef REHOST_MODE
    added();
#endif
after();
}
```

`after();` satırının girintisi kayboluyor. Eklenen conditional block’un girintisi de bulunduğu scope ile tutarlı olmayabiliyor.

Bu esas olarak apply tarafındaki insertion-index ve metin birleştirme problemi; ancak extraction’ın ürettiği anchor sözleşmesiyle doğrudan ilişkili.

Karar verilmesi gereken nokta:

* Anchor yalnızca kod metnini mi temsil edecek?
* Yoksa satır başı, indentation ve newline bilgisi de insertion sözleşmesine dahil mi olacak?

## 3. Apply sorunları

### 3.1. Aynı `match` değerine sahip transformation’lar iç içe conditional oluşturuyor — düzeltilmeli

Örneğin iki transformation da şunu arıyor:

```c
work();
```

Birinci replacement:

```c
#ifdef A
work();
#endif
```

İkinci replacement:

```c
#ifdef B
work();
#endif
```

Sonuç:

```c
#ifdef A
#ifdef B
work();
#endif
#endif
```

Sebep: `match_is_inside_replacement()` yalnızca uygulanmakta olan transformation’ın kendi replacement eşleşmelerini biliyor. Önceki transformation’ların eklediği conditional block’ların içindeki match’leri dışlamıyor.

Koruma iki tarafta da olmalı:

* Extraction aynı `file + scope + function + match` çakışmasını üretmemeli.
* Apply, dışarıdan veya elle hazırlanmış JSON’a karşı ayrıca çakışma kontrolü yapmalı.

Apply tarafında seçenekler:

* Transformation listesini uygulamadan önce çakışma doğrulaması yapmak.
* Önceden eklenmiş conditional block’ların içindeki eşleşmeleri arama bölgelerinden çıkarmak.
* Çakışan transformation’ları güvenli biçimde `SKIPPED` yapmak.

---

### 3.2. Function scope’ta bütün eşleşmeler otomatik dönüştürülüyor — düzeltilmeli veya açıkça onaylanmalı

Mevcut kontrol:

```python
if (
    len(matches_to_apply) > 1
    and transformation.get("scope") != "function"
):
```

Bu nedenle function scope’ta birden fazla eşleşmeye açıkça izin veriliyor.

Örneğin:

```c
void f(void) {
    work();
    work();
}
```

Transformation yalnızca eski rehost’taki ilk kullanım için çıkarılmış olsa bile apply ikisini de dönüştürüyor.

Konum bilgisi saklanmadığı sürece en güvenli kuralın şu olması gerektiğini düşünüyorum:

```python
if len(matches_to_apply) > 1:
    SKIPPED
```

Eğer bütün occurrence’ların değiştirilmesi bilinçli bir özellik olacaksa JSON’da bunun açıkça belirtilmesi daha güvenli olur; örneğin `replace_all: true`.


---

### 3.3. Aynı insertion içeriği iki farklı yere eklenemiyor — idempotency sözleşmesi kararı gerekli

Apply önce insertion içeriğini scope’un herhangi bir yerinde arıyor:

```python
content_matches = find_matches_in_regions(
    source_text,
    regions,
    content,
)
```

Bir tane eşleşme bulduğunda doğrudan `ALREADY_APPLIED` diyor. İçeriğin doğru anchor veya position yanında olup olmadığını kontrol etmiyor.

Bu nedenle aynı conditional block’un aynı fonksiyonda bilinçli olarak iki farklı yere eklenmesi gerekiyorsa:

* İlk insertion uygulanıyor.
* İkinci insertion, içerik başka bir konumda bulunduğu için yanlışlıkla `ALREADY_APPLIED` oluyor.

Idempotency yalnızca “content scope içinde var mı?” sorusuna dayanmamalı. Beklenen ilişki de doğrulanmalı:

```text
content + position + anchor
```

`function_start` ve `function_end` için de içeriğin beklenen fonksiyon sınırında olup olmadığı kontrol edilmeli.

Burada ürün davranışına karar verilmesi gerekiyor:

* Aynı içerik aynı scope’ta yalnızca bir kez bulunabilir mi?
* Yoksa aynı içerik farklı anchor’larda desteklenmeli mi?

---

### 3.4. `SKIPPED` dosyalar bile yeniden yazılıyor — düzeltilmeli

Bir transformation uygulanmasa bile şu kod çalışıyor:

```python
output_file.write_text(
    updated_source,
    encoding=source_encoding,
)
```

CRLF kullanan bir dosyada transformation bilinçli olarak `SKIPPED` olduğunda bile dosyanın satır sonları:

```text
\r\n → \n
```

şeklinde değişebiliyor.

Dolayısıyla rapor `SKIPPED` dese bile generated dosya byte düzeyinde değiştirilmiş oluyor.

Öneriler:

* Dosyayı `read_bytes()` ile okumak.
* Encoding ve BOM bilgisini ayrı korumak.
* Satır sonlarını dönüştürmemek.
* Yalnızca gerçekten metin değişmişse yazmak:

```python
if updated_source != source_text:
    # write
```

Daha güçlü garanti istenirse kaynak byte’ları korunmalı ve hiçbir transformation uygulanmadığında dosyaya hiç dokunulmamalı.

## 4. Encoding ve BOM

UTF-8 BOM şu anda desteklenmiyor.

Okuma sırası en azından aşağıdaki biçimde değerlendirilebilir:

```text
utf-8-sig
utf-8
cp1254
```

Ancak `utf-8-sig` ile okuyup normal `utf-8` ile yazmak BOM’u kaldırabilir. Bu yüzden yalnızca encoding adı değil, dosyada BOM bulunup bulunmadığı da korunmalı.

Bu çalışma CRLF/LF korumasıyla birlikte ele alınmalı. Ortak bir read/write yardımcı fonksiyonu kullanmak daha güvenli olacaktır.

## 5. Raporlama sorunları

### 5.1. Function boundary insertion aralıkları rapora girmiyor

`function_start` ve `function_end` işlemlerinde sonuç şu biçimde tutuluyor:

```python
"start": inserted_start,
"end": inserted_end,
```

Fakat rapor yalnızca şunu okuyor:

```python
result.get("ranges", [])
```

Bu yüzden işlem `APPLIED` olsa bile karakter aralığı raporda görünmüyor.

Sonuç diğer işlemlerle aynı sözleşmeye getirilmeli:

```python
"ranges": [
    {
        "start": inserted_start,
        "end": inserted_end,
    }
]
```

---

### 5.2. `ALREADY_APPLIED` durumunda `match_count` yanlış

Replacement iki kez bulunmuş olsa bile kod `match_count = 1` yazıyor.

Testte:

```text
replacement_match_count == 2
match_count == 1
```

çıktı.

Alanların anlamı netleştirilmeli. Önerilen ayrım:

* `match_count`: dönüştürülmemiş original match sayısı
* `replacement_match_count`: zaten uygulanmış replacement sayısı
* `applied_count`: bu çalıştırmada dönüştürülen occurrence sayısı

Bu tanıma göre `ALREADY_APPLIED` durumunda:

```text
match_count = 0
replacement_match_count = len(replacement_matches)
applied_count = 0
```

olmalı.

## 6. Öncelik ve karar özeti

Doğrudan düzeltilmesi gerekenler:

1. `__attribute__` nedeniyle yanlış fonksiyon adı.
2. Çok satırlı `#define` satırlarının signature’a karışması.
3. Birden fazla function-scope eşleşmenin otomatik değiştirilmesi veya bunun açık bir politika hâline getirilmesi.
4. Aynı `match` değerine sahip transformation çakışmaları.
5. JSON alanlarının tip doğrulaması.
6. `SKIPPED` dosyaların yeniden yazılması ve satır sonlarının değişmesi.
7. UTF-8 BOM/encoding/newline koruması.
8. Function-boundary insertion `ranges` raporlaması.
9. `ALREADY_APPLIED` sayaçlarının düzeltilmesi.

Kod yazmadan önce kapsam veya ürün kararı gerektirenler:
1. Genel C++ desteği mi, sınırlı top-level C++ desteği mi?
2. Fonksiyon pointer döndüren imzalar desteklenecek mi?
3. Preprocessor branch’lerinin brace yapıları farklı olduğunda parser nasıl davranacak?
4. Multiple match tamamen yasak mı olacak, yoksa JSON’da açık `replace_all`/konum bilgisi mi tutulacak?
5. Aynı insertion içeriğinin farklı anchor’larda kullanılması desteklenecek mi?
6. Boş replacement geçerli bir deletion işlemi mi?
7. Çakışmalı veya geçersiz parser blokları `SKIPPED`, `NEEDS_REVIEW` ya da `invalid` olarak mı gösterilecek?
